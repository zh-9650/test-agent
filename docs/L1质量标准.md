# L1 阶段质量标准

**版本**: 1.0
**制定日期**: 2026-06-09
**参考标准**: ISO/IEC/IEEE 29148, IEEE 829, ISO/IEC/IEEE 29119, INCOSE SE Handbook v4, ISTQB, REMIF Framework

---

## 一、标准概述

L1 阶段是本系统的需求分析管道，负责将原始需求文档转化为可验证的测试资产。
本标准定义 L1 各节点（Fact 提取 → Assertion 推导 → Review Gate → Goal 生成）的质量要求。

### L1 管道节点

```
PRD/Swagger/Changelog → [Fact Extractor] → RequirementFact[]
    → [Assertion Deriver] → RequirementAssertion[]
        → [Review Gate] → confirmed / blocked
            → [Goal Generator] → ExplorationGoal[]
```

### L1 Agentic 质量补充原则

L1 不只是传统需求抽取器，还承担 Runtime Test Agent 的上游契约职责。因此除需求工程指标外，还必须增加以下 AI-native 质量门：

| 维度 | 第一轮门槛 | 说明 |
|------|------------|------|
| 确定性 unsupported | 0% | 缺 source、quote、无效 fact_id、悬空引用等结构性 unsupported 必须为 0 |
| Groundedness 抽检 | 人工校准 | 语义 unsupported 不能只靠 LLM 自动判定，需人工校准样本 |
| Source Registry | 100% | 非 inferred fact 必须可定位到 source_id、content_hash、offset/quote_hash |
| Review Gate 一致性 | 100% | Phase 1 与 Phase 2 必须调用同一门禁规则 |
| Strict Goal 完整率 | 100% | Goal 必须包含 id、assertion_refs、expected_evidence、stop_condition、priority |
| Traceability 悬空引用 | 0 | Fact→Assertion→Condition→Coverage→CandidateCase 不允许断链 |
| CandidateCase 权威输入 | M2 验收 | CandidateCase 必须进入 Runtime，不再只是事后分析包 |
| 运行结果幂等 | M3 验收 | 执行结果以 CaseResult/ExecutionRun 为权威，计数由结果集合聚合 |
| 数据集健康 | M4 验收 | Golden Dataset 需覆盖正常、边界、权限、冲突、模糊和对抗输入 |

## 二、Fact 提取质量标准

### 2.1 原子性 (Atomicity)

**参考**: ISO/IEC/IEEE 29148 §6.2 — 每条需求应表达单一、可验证的事实

| 指标 | 标准 | 当前值 | 说明 |
|------|------|--------|------|
| 原子事实率 | ≥95% | ~90% | 复合陈述应拆分为多条事实 |
| Subject 长度 | ≤30 字符 | 待测 | 过长说明未充分拆分 |
| 每页事实密度 | 5-15 条/文档 | 视文档而定 | 过低=遗漏，过高=过度拆分 |

### 2.2 完整性 (Completeness)

**参考**: IEEE 29148 §6.1 — 需求应充分描述系统行为，无遗漏

| 指标 | 标准 | 当前值 | 说明 |
|------|------|--------|------|
| 模块覆盖率 | 100% (9/9) | 100% ✅ | 所有需求模块均需提取 |
| 字段完整率 (subject/action/object) | 100% | 100% ✅ | 核心字段不可为空 |
| Quote 完整率 | ≥95% | 100% ✅ | 每条事实必须有原文引用 |
| Condition 填写率 | ≥40% | 34% ⚠️ | 有条件的事实必须填写 |
| Outcome 填写率 | ≥50% | 64% ✅ | 有结果的事实必须填写 |

### 2.3 一致性 (Consistency)

**参考**: IEEE 29148 §6.2 — 需求之间不应矛盾

| 指标 | 标准 | 当前值 | 说明 |
|------|------|--------|------|
| 冲突检测率 | 100% | 待测 | 检测到的冲突必须标记 |
| 状态标记率 | 100% | 待测 | conflicted/superseded 状态必须标注 |
| Subject 去重率 | ≤10% 重复 | ~12% ⚠️ | 同一 subject 不应出现过多 |

### 2.4 可追溯性 (Traceability)

**参考**: IEEE 29148 §6.4, ISTQB — 每条需求必须可追溯到来源

| 指标 | 标准 | 当前值 | 说明 |
|------|------|--------|------|
| Source Reference 覆盖率 | 100% | 100% ✅ | 每条事实必须有来源引用 |
| Source Type 准确率 | ≥90% | 待测 | prd/swagger/changelog 等分类准确 |
| 跨文档引用率 | ≥20% | 待测 | 事实应能关联多个来源 |

### 2.5 置信度 (Confidence Calibration)

**参考**: Evidence-based Requirement Analysis, Conformal Prediction

| 指标 | 标准 | 当前值 | 说明 |
|------|------|--------|------|
| Confidence <1.0 比例 | ≥30% | 74.0% ✅ | LLM 不应全部给满分 |
| Confidence 分布熵 | ≥1.5 bits | 待测 | 分布应有足够多样性 |
| 低置信度事实占比 | 5-15% | 1.4% ⚠️ | <0.7 的事实应有但不多 |
| 校准一致性 | ±0.1 | 待测 | 校准后与证据质量一致 |

## 三、Assertion 推导质量标准

### 3.1 可验证性 (Verifiability)

**参考**: IEEE 29148 §6.3, INCOSE SE Handbook — 每条需求必须可验证

| 指标 | 标准 | 当前值 | 说明 |
|------|------|--------|------|
| 可验证断言率 | 100% | ~92% | 每条断言必须可观察/可测量 |
| 断言文本长度 | 30-150 字符 | 61 avg ✅ | 过短=不明确，过长=不原子 |
| 短断言占比 (<30字符) | ≤10% | 8% ✅ | 需展开为完整测试步骤 |

### 3.2 完整性 (Coverage)

**参考**: ISTQB — 100% 需求覆盖率

| 指标 | 标准 | 当前值 | 说明 |
|------|------|--------|------|
| Facts-to-Assertions 覆盖率 | ≥80% | ~85% ✅ | 大部分 facts 应产生 assertions |
| Assertion 类型覆盖 | ≥6 种/8 种 | 7/8 ✅ | 应覆盖所有断言类型 |
| 无引用断言率 | 0% | 0% ✅ | 每条断言必须引用 fact |

### 3.3 追溯深度 (Traceability Depth)

**参考**: INCOSE — 断言应关联多个需求以实现交叉验证

| 指标 | 标准 | 当前值 | 说明 |
|------|------|--------|------|
| 多事实引用断言占比 | ≥20% | 0% ❌ | 断言应关联 2+ facts |
| 平均引用事实数 | ≥1.5 | 1.0 ❌ | 过低=缺少交叉验证 |
| 最大引用事实数 | ≤6 | 1 ❌ | 过高=过于宽泛 |

### 3.4 风险分级 (Risk Classification)

**参考**: ISTQB Risk-based Testing, ISO 29119

| 指标 | 标准 | 当前值 | 说明 |
|------|------|--------|------|
| High 风险占比 | 10-25% | 13% ✅ | 安全/权限/数据完整性 |
| Medium 风险占比 | 40-60% | 73% ⚠️ | 核心功能逻辑 |
| Low 风险占比 | 10-25% | 14% ✅ | UI/边缘功能 |
| 风险分布合理性 | 符合正态 | 偏 medium | 应有合理梯度 |

## 四、Review Gate 标准

**参考**: Risk-based Testing, ISO 29119 §5.5

| 指标 | 标准 | 当前值 | 说明 |
|------|------|--------|------|
| 拦截率 | 10-20% | 11.1% ✅ | 过高=效率低，过低=遗漏风险 |
| Security 类拦截率 | 100% | 100% ✅ | 安全断言必须人工确认 |
| Data_rule 类拦截率 | ≥80% | 100% ✅ | 数据规则断言需确认 |
| Functional 类拦截率 | ≤5% | 0% ✅ | 功能断言直接放行 |
| 误拦截率 | ≤5% | ~0% ✅ | 不应拦截低风险断言 |

## 五、Goal 生成标准

**参考**: Test Prioritization, Risk-based Test Ordering

### 5.1 优先级分层

| 指标 | 标准 | 当前值 | 说明 |
|------|------|--------|------|
| Priority 层数 | ≥3 | 3 ✅ | high/medium/low |
| High 优先级占比 | 15-30% | 24% ✅ | 安全/数据规则相关 |
| Medium 优先级占比 | 40-60% | 57% ⚠️ | 核心功能 |
| Low 优先级占比 | 5-20% | 4% ⚠️ | 偏低，应增加 |
| 无优先级 Goals | 0% | 0% ✅ | 所有 goals 必须有优先级 |

### 5.2 可执行性

| 指标 | 标准 | 当前值 | 说明 |
|------|------|--------|------|
| 动作化 Goals 占比 | ≥80% | ~100% ✅ | 应以"验证:"开头 |
| Goal 文本长度 | 40-120 字符 | 待测 | 过短=不明确，过长=不聚焦 |
| 验收标准明确率 | ≥50% | ~30% ⚠️ | Goal 应包含验收条件 |

## 六、模块均衡标准

**参考**: Completeness — 需求覆盖应均衡，不应过度集中

| 指标 | 标准 | 当前值 | 说明 |
|------|------|--------|------|
| 最大/最小模块比 | ≤5x | 9.3x ❌ | 应控制在 5 倍以内 |
| Facts <5 的模块数 | ≤2 | 3 ⚠️ | 过少=可能遗漏 |
| Facts >30 的模块数 | ≤1 | 1 ✅ | 过多=可能冗余 |
| 模块间标准差 | ≤8 | ~9 ⚠️ | 应控制分布 |

## 七、综合评分模型

### 7.1 权重分配

| 维度 | 权重 | 说明 |
|------|------|------|
| Fact 完整性 | 25% | 字段完整、quote 覆盖 |
| Assertion 可验证性 | 20% | 断言可测试、类型覆盖 |
| 追溯深度 | 15% | 多事实引用、跨模块关联 |
| 置信度校准 | 15% | 分布合理、无过度自信 |
| 模块均衡性 | 10% | 分布均匀、无遗漏 |
| Review Gate 效率 | 10% | 拦截率合理 |
| Goal 可执行性 | 5% | 优先级分层、动作化 |

### 7.2 评分等级

| 等级 | 分数范围 | 含义 |
|------|---------|------|
| A (优秀) | 90-100 | 所有指标达标，可直接进入 L2 |
| B (良好) | 75-89 | 大部分达标，少量改进 |
| C (及格) | 60-74 | 基本可用，需改进 |
| D (不及格) | <60 | 需要重大修复 |

| 维度 | 得分 | 说明 |
|------|------|------|

| Assertion 可验证性 | 82/100 | 类型覆盖好，短断言需展开 |
| 追溯深度 | 40/100 | 全部单事实引用，需增强 |
| 置信度校准 | 95/100 | 74%<1.0，分布合理 |

| **综合** | **76/100** | **B 级 (良好)** |

## 八、达标路线图

### Phase 1: 已完成 ✅ (2026-06-09)

- [x] Goals 优先级三层分层
- [x] Confidence 后处理校准 (74%)
- [x] Review Gate 优化 (11.1%)
- [x] Assertion 类型覆盖 (7/8)

### Phase 2: 待实施 (高优先级)

- [ ] **追溯深度增强**: assertion_deriver 生成跨 2-3 facts 的复合断言 (目标: ≥20%)
- [ ] **模块均衡化**: 对 facts <5 的模块增加提取力度 (目标: 比值 ≤5x)
- [ ] **Subject 去重**: fact_extractor 增加去重逻辑 (目标: ≤10%)

### Phase 3: 待实施 (中优先级)

- [ ] **Condition 覆盖提升**: 鼓励提取条件分支逻辑 (目标: ≥40%)
- [ ] **Goal 验收标准**: 每个 goal 包含明确验收条件 (目标: ≥50%)
- [ ] **Low 优先级 Goals**: 增加边缘/异常场景 goals (目标: ≥10%)

### Phase 4: 长期优化

- [ ] **性能断言覆盖**: 补充性能/并发/响应时间断言 (目标: ≥5%)
- [ ] **跨模块关联**: 事实间建立依赖关系图
- [ ] **Ground Truth 对比**: 建立标准答案集，计算 Precision/Recall/F1
